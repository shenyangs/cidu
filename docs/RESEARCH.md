研究日期：2026-10-24。以下是读取到的项目材料与本机实验结论，不代表厂商承诺。

项目声称支持一种格式，并不证明兼容当前 Mac 私有用户库。例如百度 `.bin` 可能指备份格式，而非运行时的 `usr3user.bin`。因此当前使用百度自带导出入口。

## 用户提供的 Windows 工具

对用户提供的 EXE 只做离线归档与 Python 字节码分析，没有运行该程序。样本为 PyInstaller 打包，内部是 Python 3.13 字节码。静态分析看到搜狗二进制、文本和豆包文件相关路径，不能据此宣称它支持百度 Mac 运行时词库。

工具的重建路径可以增加索引/数据区大小，但 Windows 程序中的逻辑不能代替 Mac 引擎验证。其代码与常量表未合入本项目，也不随本项目分发。

## 豆包 macOS 格式要点

本次检查版本为 1.0.2；实际用户文件在 Application Support 下的账号目录，不能只查社区材料中的旧 `dict/usr.dat` 路径。

目前识别的头部包含 magic `12001`、版本 `20230630`、64 字节头、音节表区、4 字节偏移索引与数据区。解码时检查区间关系、长度、记录边界和编码；未知结构拒绝继续。词语采用 UTF-16 编码单元的旋转/XOR 表示，拼音另有字节变换。它不是可依赖的保密加密。

一个重要更正：头部中的 `80000` 是索引区**字节数**，对应 20,000 个四字节槽位，并非 80,000 个词条上限。当前槽位数也不等同于引擎固定上限。本机 1.0.2 已通过 40,000 槽位的加载、学习、保存和重启检查。

原先的计数差已定位：offset=0 在已用索引前缀内是有效记录。原库完整计数为 17,537。索引应按音节 ID 数值序列排序，不能按小端序字节串排序；数据 cursor 为记录末端，不减 1。详见 VALIDATION.md。

## 仍未解决

- 百度本机官方导出与用户预期的历史词库总数为何不同：需核查账号、云端同步与产品计数口径。
- 其他版本格式兼容，以及 1 条非标准输入的候选可达性。
- 长期云同步与跨设备是否保留，更新版本后是否仍兼容。
- 历史词频、排序、上下文学习信息能否映射。目前仅承诺保留可导出的词语、读音和原始数值。
